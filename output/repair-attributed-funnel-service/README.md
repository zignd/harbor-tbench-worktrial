# Repair the Attributed Funnel Service

A backend developer is chasing a production discrepancy in an internal campaign-funnel service. The container contains a Python HTTP service, a SQLite-backed event store, materialized SQL stages, replay tooling, fixtures, and several unrelated operational modules. The service is already deployable, but reports become unreliable after realistic event history accumulates and late events are replayed.

## What it tests
- The solver fixes the visible baseline query but does not trace the append-time materialization and therefore leaves stale downstream rows after late corrections.
- The solver recomputes sessions but forgets to rebuild attribution or order-level refund aggregates that depend on them.
- The solver uses append order or a non-unique timestamp window ordering, producing nondeterministic results for ties.
- The solver interprets the 1,800-second boundary or report end timestamp incorrectly.
- The solver attributes refunds by amount, session, or campaign rather than following the referenced order ID.
- The solver treats duplicate event IDs as first-write-wins or permanently deletes the old winner without rebuilding affected users.
- The solver validates only the bundled fixture and misses verify-time histories with interleaved users, repeated refunds, and adversarial batch boundaries.
- The solver changes the protocol or launcher while repairing SQL, causing service-level tests to fail despite locally correct calculations.

## Verification
- Start-up and protocol test: launches `./run.sh`, checks `/health`, validates all required status codes and JSON shapes, and confirms the process binds on port 8080.
- Fixture baseline test: resets the service, appends the supplied historical fixture in its normal order, requests several date ranges and campaign filters, and compares exact rows, integer revenues, and ordering.
- Duplicate-history test: generates events with duplicate IDs whose winning ingest sequence arrives late, appends them in multiple permutations, and requires identical reports and idempotent replays.
- Session-boundary test: generates users with gaps below, exactly at, and just above 1,800 seconds, including equal timestamps and shuffled ingest order, then checks session counts and downstream attribution.
- Late-event dependency test: appends a purchase and report first, then appends an earlier touch that changes the purchase's session or campaign; the subsequent report must reflect the rebuilt chain of derived results.
- Refund test: generates purchases and refunds in different sessions and batches, including repeated refunds and misleading equal amounts, and checks that only the referenced order is reversed once under its original attribution.
- Date/filter test: generates events exactly at `since` and `until`, uses empty and nonempty campaign filters, and verifies half-open interval behavior and zero rows for explicitly requested campaigns.
- Randomized verify-time test: for several hidden seeds, generates hundreds to thousands of events across users and campaigns, partitions them into adversarial append batches, and compares every report against an independent reference implementation.
- State-isolation test: performs reset, runs a second unrelated history, and verifies that no sessions, orders, or materialized rows from the first history leak into the second.
- Resource and repeatability test: repeats representative reports and replay sequences to ensure deterministic JSON output and acceptable completion within the container's CPU and memory limits.
