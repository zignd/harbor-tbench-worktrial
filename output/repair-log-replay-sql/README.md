# Repair the Log Replay SQL Pipeline

A data engineer inherited an incident-log replay job that turns sharded service logs into session and latency metrics, but the current release silently drops or invents records. The container contains the replay runner, SQLite schemas and queries, a small opaque line-decoding helper, fixtures, and operational notes; please make the existing command trustworthy for the next backfill.

## What it tests
- The solver reads the visible SQL and patches coercion or filtering without experimentally characterizing the opaque decoder.
- The implementation uses a normal JSON parser with last-key-wins behavior and cannot reject duplicate keys or distinguish integers from numeric strings.
- Deduplication is performed before retaining source coordinates, so equal timestamps or cross-shard duplicates select the wrong record.
- A session is marked valid while invalid members are silently discarded, rather than invalidating the entire session.
- Metrics are computed in an earlier stage and are not recomputed after lifecycle validation.
- The p95 implementation uses interpolation, floor ranking, or floating-point rounding instead of the specified nearest rank.
- CSV writers append to existing files or trust stale stage directories after interruption.
- The solver assumes normal UTF-8 newline behavior and loses records or line numbers around decoder block boundaries.
- Filesystem traversal order leaks into output ordering.
- A partial repair passes the small fixture but compounds tiny event-level errors into large session and percentile discrepancies in the generated corpus.

## Why the model fails it
- weak_verification: The implementation allowed the JSON parser to classify the unescaped control byte as `invalid_json`, violating the required stable reason `control_character`. In step 5 the agent explicitly identified that control-character classification might be imperfect, but it did not fix or test that case before declaring completion in steps 8–9.
- weak_verification: The implementation classified the unescaped control-character line as `invalid_json`, violating the explicitly required stable reason. At steps 6-7 the agent itself recognized that control-character classification was insufficient and planned adversarial tests, but at steps 8-9 it stopped and declared success without running them or correcting the issue.

## Verification
- Run the command on the visible fixture and compare all four CSV files, including headers, ordering, quoting, and reject reasons.
- Generate fresh valid and invalid JSONL shards with randomized directory names and filesystem creation order, then compare every output row with an independent strict-parser oracle.
- Exercise malformed UTF-8, duplicate keys, extra keys, control characters, wrong JSON types, range violations, and SQL-like tenant/session/event strings; verify bad lines are rejected without dropping unrelated good lines.
- Place valid and invalid lines around CRLF boundaries, escaped characters, unterminated final lines, and the opaque helper's block boundaries; verify recovery and physical line numbering.
- Generate duplicate event IDs across files and equal timestamps, checking the complete tie-breaking tuple and deterministic accepted-event order.
- Generate sessions with missing or repeated lifecycle events, out-of-range timestamps, invalid members, and valid interleavings; verify rejected sessions contribute no rows to either session or metric results.
- Compare metric counts, sums, maxima, and nearest-rank p95 values for thousands of generated events, including n values where percentile interpolation would differ from nearest-rank selection.
- Run with randomized file enumeration order and confirm byte-identical outputs.
- Interrupt or remove stage artifacts between stages, rerun into an existing output directory, and verify atomic recovery, idempotence, and absence of duplicate CSV rows.
- Run a scale corpus with many shards and rare adversarial records to ensure the solution does not rely on manual inspection or sampling.

## Known caveat (quality rubric)

The pipeline's `harbor check` quality rubric flagged `behavior_in_tests` on the calibrated package: the
tests cover the core behaviors (validation, recovery, deduplication, sessions, metrics, quoting, reruns,
argument count, unterminated input, p95) but not every boundary the instruction documents. The task is
shipped anyway because it fits the band (1 of 3 judged runs passed, both failures valid, no hacked pass)
and passes the structural validator, an independent oracle 3/3 and nop; the coverage gap is a
limitation, not a validity or difficulty problem. A future revision should add tests for the remaining
documented boundaries.
