# Repair the release packager

A backend developer is chasing a production incident where releases occasionally contain the wrong build variant and cannot be reproduced from the CI evidence. The container contains an internal Python release-packaging tool with a shell-driven, three-stage pipeline: it normalizes build logs, resolves the dependency closure for a requested release, and emits a deterministic artifact archive plus build metrics.

## What it tests
- Selecting the last textual event instead of grouping attempts and applying terminal-attempt semantics.
- Using a filename, short name, or digest as the dependency identity and silently merging distinct variants.
- Applying platform selection only at the roots or only at the first dependency level rather than throughout the closure.
- Counting catalog entries or log records in metrics instead of counting the final reachable and packaged set.
- Publishing a partial archive after an integrity error or failing to validate payload bytes against catalogued digests.
- Leaving tar or gzip timestamps, ownership, member order, JSON ordering, or locale-dependent sorting nondeterministic.
- Implementing correct graph semantics with an O(events × jobs) or O(edges × catalog) algorithm that misses the performance threshold.
- Testing only the visible linear fixture and never constructing histories with retries, permutations, selector collisions, or diamond dependencies.

## Why the model fails it
- partial_implementation: The implementation used an insufficient release.yaml parser and did not handle the valid JSON-formatted YAML used by the fixture, so it failed to read the roots and emitted an empty artifact list. In step 10 it only tested a conventional YAML fixture, and in step 12 it declared success after that narrow smoke test without validating closure contents or the hidden fixture format.
- partial_implementation: The agent implemented only a limited line-oriented YAML parser, which failed on the fixture's valid JSON-formatted YAML and raised `KeyError: 'platform'`. Its synthetic test used multiline simple YAML instead, so it did not verify the actual input representation before stopping at step 10.

## Verification
- A basic valid-fixture test invokes the documented CLI and checks that the archive, manifest, and metrics sidecar are created with the exact reachable artifact set.
- A generated retry-history test permutes and expands build attempts, including failed and superseded attempts, and checks that the manifest contains only the highest terminal attempt with successful status; this checks the requirement that exactly one terminal successful build attempt is selected per logical job.
- Generated platform and variant fixtures include generic fallbacks, platform-specific overrides, punctuation-bearing identities, and irrelevant jobs; the verifier compares the selected transitive closure and manifest fields with the reference, checking the platform/variant dependency requirement.
- Generated diamond and duplicate-content graphs check that all reachable logical identities are represented, each payload digest is stored once, and dependency edges are not lost through digest-based conflation.
- Mutation tests delete an artifact or alter its bytes while leaving the catalog digest unchanged and require a nonzero exit with no successful published package, checking integrity validation.
- Reproducibility tests reorder every input file, change artifact and input mtimes, run under several locales, and write to different temporary directories; the verifier compares archive bytes and canonical manifest/metrics bytes.
- Metrics tests compare selected jobs, excluded jobs, traversed edges, artifact count, payload bytes, and cache hits against the final reference closure, including fixtures with many failed irrelevant jobs.
- A hidden scale fixture generated from a seed contains tens of thousands of interleaved events and thousands of catalog entries; the verifier requires correct output and wall-clock completion below 6 seconds on the one-CPU container.
