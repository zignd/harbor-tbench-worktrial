Preserve the existing request and response field names and one-JSON-object-per-line framing for health, append, query, rotate, verify, and reset requests.

Health must report a successful status. Append requests contain type "append", tenant, integer seq, and payload as hexadecimal bytes; successful responses must include tenant, epoch, seq, payload, mac, and root. Query requests contain tenant and may contain epoch, seq_min, seq_max, prefix, offset, and limit. They must return exactly matching events with tenant, epoch, seq, payload, and mac fields, plus total, offset, and limit. Payload-prefix matching is byte-based, payloads are binary-safe, pagination occurs after numeric sequence ordering, and records from other tenants must never appear.

Rotate requests contain tenant and return the tenant's new epoch and root. Verify requests contain tenant and must strictly validate stored MACs and roots and report the current root. Reset requests with a tenant affect only that tenant; records outside the requested scope must remain. Existing records must not be discarded, and SQLite state in /opt/audit/state/audit.sqlite, service responses, and sealing-daemon responses must agree.

Use the supplied sealing daemon and its documented byte-exact encoding for every cryptographic operation: tenant and payload are bytes, sequence and length values are fixed-width big-endian integers, and NUL and non-UTF-8 payload bytes must round-trip. Preserve independent state for multiple tenants and epochs. Verification must remain valid after arbitrary mixtures of appends, queries, rotations, resets, and restarts, including sequence values 0, 1, 2, 9, 10, 255, 256, and larger values. Keep the existing startup interface and wire protocol; do not weaken verification or replace the service with a different protocol.
