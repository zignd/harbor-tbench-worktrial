====================================================================
DEPLOYMENT RUNBOOK: Shard Allocator Migration
====================================================================

Pre-flight checks:
  [ ] Verify allocator binary is present at /usr/local/bin/allocator
  [ ] Verify SQLite3 is installed (apt-get install sqlite3)
  [ ] Verify /app/sample_data.csv is readable
  [ ] Verify /app/setup.sql creates the queries table correctly

Deployment steps:
  1. Stop the dispatch daemon: systemctl stop query-dispatcher
  2. Backup current assignments: cp /var/lib/allocator/state.db /backup/
  3. Run the new SQL allocator: sqlite3 /app/allocator.db < /app/solution/allocate.sql
  4. Compare outputs with legacy binary using diff
  5. If match, restart dispatcher with SQL-based config
  6. If mismatch, rollback: systemctl stop query-dispatcher && cp /backup/state.db /var/lib/allocator/

Rollback plan:
  - Revert config flag 'use_sql_allocator' to false
  - Restart dispatch daemon
  - Investigate discrepancies before next attempt

Monitoring:
  - Watch /var/log/dispatch/allocator.log for errors
  - Check Grafana dashboard "Shard Load Distribution" for imbalance


=== SECTION B: Troubleshooting Common Deployment Failures ===

Failure: "Error: cannot open /app/allocator.db"
Cause: The database file was not created before running allocate.sql.
Fix: Run `sqlite3 /app/allocator.db < /app/setup.sql` first.

Failure: "Parse error: no such table: queries"
Cause: The queries table was not created before importing CSV.
Fix: Ensure setup.sql creates the table before importing.

Failure: "Runtime error: recursive CTE exceeded depth"
Cause: Input CSV has too many rows (SQLite recursion limit reached).
Fix: Split the CSV into batches of 40,000 rows and merge results.

Failure: "AssertionError: Mismatch in test cases"
Cause: The SQL solution does not exactly replicate the binary's behavior.
Fix: Carefully study how the binary orders queries and assigns shards.
     Run the binary on small custom CSVs with duplicate values to observe
     the precise ordering and tie-breaking rules. Pay special attention
     to what happens when loads are equal but timestamps differ, and
     when both loads and timestamps are identical.


=== SECTION C: Post-Migration Verification Checklist ===

[ ] All test cases from verify.py pass (NUM_TESTS=100).
[ ] Edge cases verified: empty input, single query, 1000 queries, all equal loads.
[ ] Performance: 10,000 queries complete in < 30 seconds.
[ ] Output is byte-for-byte identical to allocator binary for 100 random inputs.
[ ] Rollback documented: switch config toggle `use_sql_allocator = false`.
[ ] Monitoring alert thresholds reconfigured for SQL-based allocator latency.
